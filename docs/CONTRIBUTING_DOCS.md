# 📝 Регламент и правила обновления документации NijiPanel

> **⚠️ ЗОЛОТОЕ ПРАВИЛО ПРОЕКТА:**  
> **Любой новый функционал, изменение эндпоинта REST API, параметров DTO или добавление команды в `commands.json` ОБЯЗАТЕЛЬНО и БЕЗОГОВОРОЧНО должны сопровождаться обновлением документации в папке `docs/` в рамках того же самого Pull Request!**

Документация NijiPanel — это не вторичный артефакт, а неотъемлемая часть кодовой базы. Код без актуальной документации считается незавершенным и не принимается в ветку `main`.

---

## 📌 1. Строгие правила синхронизации изменений

### Правило 1.1: Изменение REST API
Если вы:
* Добавили новый контроллер или действие (эндпоинт);
* Изменили сигнатуру существующего эндпоинта (URL, HTTP-метод, query-параметры);
* Изменили поля запроса или ответа (Request/Response DTO);
* Изменили коды возвращаемых ошибок HTTP (400, 401, 403, 404, 500);

👉 **Вы обязаны:**
1. Обновить таблицу в [REST API Reference](api.md).
2. Привести актуальный пример запроса и ответа (JSON + cURL).
3. При необходимости обновить соответствующий тематический раздел документации (например, [docker.md](docker.md) при изменениях в `DockerController`).

---

### Правило 1.2: Изменение системных команд (`commands.json`)
Если вы:
* Добавили новую команду в `commands.json`;
* Изменили bash-скрипт команды или используемые аргументы/плейсхолдеры `{...}`;
* Изменили дефолтный таймаут команды `timeoutSeconds`;
* Добавили новую категорию команд;

👉 **Вы обязаны:**
1. Обновить общее количество команд и таблицу категорий в [commands-registry.md](commands-registry.md).
2. Задокументировать логику команды и ее поведение на разных дистрибутивах.
3. Проверить, что команда содержит безопасные проверки (`command -v`, `2>/dev/null`, обработку ошибок).

---

### Правило 1.3: Изменения в интерфейсе (UI) и UX
Если вы:
* Добавили новый экран, модальное окно или вкладку;
* Добавили новую дизайн-константу, цвет или токен;
* Изменили поведение навигации или горячих клавиш;

👉 **Вы обязаны:**
1. Сделать актуальный скриншот в разрешении не менее 1280x800 px.
2. Сохранить скриншот в директорию `screenshots/` и скопировать в `docs/screenshots/`.
3. Обновить описание в соответствующем файле модуля и в [design-system.md](design-system.md).
4. Проверить соблюдение **правила 0px border-radius** и палитры **IBM Carbon Dark** (`#0d0e12`) / **Dorito Yellow** (`#ffd100`).

---

### Правило 1.4: Переменные окружения и конфигурация
Если вы:
* Добавили новую переменную окружения в бэкенд или `docker-compose.yml`;
* Изменили порт по умолчанию или пути монтирования томов;

👉 **Вы обязаны:**
1. Внести переменную в таблицу в [quickstart.md](quickstart.md#переменные-окружения).
2. Обновить примеры в `README.md` и в `docker-compose.yml`.

Перед отправкой Pull Request скопируйте и заполните следующий чеклист в описание вашего PR:

```markdown
### 📝 Проверка синхронизации документации (Doc Sync Checklist)
- [ ] Отражены все новые эндпоинты API в `docs/api.md` (с примерами JSON/cURL).
- [ ] Обновлены затронутые команды и шаблоны в `docs/commands-registry.md`.
- [ ] Добавлены пояснения в тематические модули (`docs/docker.md`, `docs/fleet.md` и др.).
- [ ] При изменениях UI сделаны и добавлены новые скриншоты в `docs/screenshots/`.
- [ ] Проверена валидность ссылок в `docs/_sidebar.md` и `docs/_navbar.md`.
- [ ] Локально проверена сборка документации и отсутствие сломанного синтаксиса Markdown.
```

## 🔍 3. Локальная проверка документации перед коммитом

Поскольку документация NijiPanel использует Docsify, для локального предпросмотра сайта достаточно запустить любой легковесный HTTP-сервер в корне репозитория или в папке `docs/`:

```bash
# Вариант 1: через Python
cd docs && python3 -m http.server 3000

# Вариант 2: через npx docsify-cli
npx docsify-cli serve docs

# Вариант 3: через npx serve
npx serve docs
```

Откройте адрес `http://localhost:3000` в браузере и убедитесь:
1. Корректно работает полнотекстовый поиск.
2. Ссылки в боковом меню (`_sidebar.md`) открывают нужные страницы без 404.
3. Блоки кода подсвечиваются правильными цветами.
4. Скриншоты и SVG-логотипы отображаются корректно.

## 🎨 4. Стилевые требования к оформлению страниц

1. **Заголовки и структура:**
   * Заголовок первого уровня `#` — только один раз в самом начале документа.
   * Четкая разбивка на разделы `##` и подразделы `###`.
   * Использование списков, таблиц и выделений ключевых терминов полужирным шрифтом.
2. **Блоки кода:**
   * Всегда указывайте язык подсветки для тройных кавычек: ```` ```bash ````, ```` ```json ````, ```` ```csharp ````, ```` ```yaml ````.
3. **Ссылки на файлы:**
   * Все относительные ссылки внутри документации оформляются в виде Markdown-ссылок на `.md` файлы (например, `[Архитектура](architecture.md)`). Docsify автоматически преобразует их в клиентский роутинг хэша (`#/architecture`).
